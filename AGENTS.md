# AGENTS.md — YTDLP GUI Mangar

Этот файл содержит постоянные правила проекта для Codex и других coding-agent'ов. Правила обязательны, если пользователь явно не дал противоположную инструкцию.

## 1. Язык и коммуникация

- Общение с пользователем — на русском языке.
- Итоговые отчёты, release notes, CHANGELOG и commit messages — на русском языке.
- Пользовательские ошибки и статусы приложения — на русском языке.
- Сырой вывод `yt-dlp`, `ffmpeg`, `ffprobe`, Go, npm и других внешних инструментов НЕ переводить: сохранять оригинальный stderr/stdout в технических логах.
- Не писать длинные отчёты без необходимости. Сначала результат, затем важные детали и найденные риски.

## 2. Главная цель продукта

YTDLP GUI Mangar — минималистичный Windows GUI для `yt-dlp`.

Основной сценарий:
1. пользователь вставляет одну ссылку или импортирует `.txt` со ссылками;
2. выбирает папку назначения;
3. приложение скачивает максимально доступное качество видео и максимально доступное качество аудио;
4. аудио и видео объединяются через FFmpeg;
5. итоговый пользовательский файл — MP4;
6. очередь выполняет максимум 3 задания одновременно.

Приложение не должно превращаться в интерфейс со всеми флагами `yt-dlp`.

## 3. Неподлежащие самовольному изменению продуктовые решения

- Windows 10/11 first.
- Backend: Go.
- Frontend: React + TypeScript.
- Desktop shell: Wails v2 stable на старте проекта.
- Не связывать download-engine напрямую с UI/Wails: бизнес-логика должна быть тестируемой отдельно.
- `yt-dlp`: использовать `-N 8` (`--concurrent-fragments 8`) для поддерживаемых fragmented downloads.
- Максимум 3 активные загрузки одновременно.
- Лучшее доступное видео + лучшее доступное аудио имеют приоритет над удобством контейнера.
- После скачивания объединять потоки через FFmpeg.
- Целевой пользовательский контейнер — MP4.
- Сначала пытаться получить MP4 без лишнего перекодирования. Если выбранные лучшие кодеки не могут быть корректно помещены в MP4, разрешено перекодировать только то, что необходимо для успешного MP4-результата.
- Для batch-импорта порядок ссылок фиксируется при импорте и не зависит от порядка завершения загрузок.
- Batch-файлы именуются `1.mp4`, `2.mp4`, `3.mp4`, ... согласно позиции в исходном TXT.
- Retry не создаёт новый порядковый номер: повторяет исходное задание.
- Лимит 3 и `-N 8` не выносить в UI первой версии как пользовательские настройки.

## 4. UX-принципы

- Минимум элементов. Не добавлять функции «на всякий случай».
- Две основные вкладки слева: `Загрузка` и `Настройки`.
- Компактная боковая панель.
- Небольшие кнопки и плотные строки очереди.
- Никаких гигантских CTA, карточек на пол-экрана или dashboard-стиля.
- Frameless window с собственной верхней панелью.
- Окно обязано корректно работать при DPI 100%, 125%, 150% и при минимальном поддерживаемом размере.
- Использовать системный стек шрифтов Windows (`Segoe UI Variable`, `Segoe UI`, system-ui), без обязательной загрузки web-fonts.
- Не подключать тяжёлую UI-библиотеку без явной необходимости.
- Действия строки очереди зависят от состояния. Не показывать постоянно набор из 4–6 кнопок.

## 5. Очередь и состояния

Минимальные состояния задания:
- `queued` — в очереди;
- `preparing` — подготовка/получение метаданных;
- `downloading` — скачивание;
- `merging` — объединение/обработка FFmpeg;
- `completed` — завершено;
- `failed` — ошибка;
- `cancelled` — отменено;

По явному решению пользователя в Этапе 7 очередь хранится только в памяти. После настоящего Exit, crash или reboot она исчезает. Persistence очереди, session recovery и состояние `interrupted` не входят в текущий roadmap. Готовые MP4 и технические логи сохраняются.

## 6. Процессы и безопасность

- Никогда не собирать команду через shell-конкатенацию пользовательского URL или пути.
- Использовать `exec.CommandContext`/эквивалент с отдельными аргументами.
- Корректно поддерживать пути с пробелами, кириллицей, Unicode, `&`, `%`, кавычками и длинными именами.
- Каждое задание получает стабильный внутренний UUID/ID.
- Каждое активное задание использует отдельный temp-каталог.
- Не допускать коллизий `.part`, intermediate video/audio и выходных файлов между тремя worker'ами.
- При отмене завершать дерево дочерних процессов `yt-dlp`/FFmpeg настолько корректно, насколько позволяет Windows, закрывать pipes и чистить только temp данного задания.
- Никогда не удалять готовый пользовательский файл только потому, что пользователь удалил карточку задания из истории.
- Перед перезаписью существующего файла применять заранее определённую политику; не уничтожать файл молча.

## 7. Зависимости

Приложение управляет минимум:
- `yt-dlp.exe`;
- `ffmpeg.exe`;
- `ffprobe.exe`;
- JS runtime (по текущей архитектуре — Deno), если он требуется актуальной конфигурации `yt-dlp`.

Рекомендуемое хранение:
`%LOCALAPPDATA%\\YTDLPGUIMangar\\tools\\`

Другие данные:
- настройки: `%LOCALAPPDATA%\\YTDLPGUIMangar\\data\\`;
- очередь: только в памяти, без файлов состояния;
- логи: `%LOCALAPPDATA%\\YTDLPGUIMangar\\logs\\`;
- временные данные: `%LOCALAPPDATA%\\YTDLPGUIMangar\\temp\\<job-id>\\`.

Не менять эти пути без миграции и документированного решения.

## 8. Логи

- Пользовательский UI показывает короткое понятное русское сообщение.
- Технический лог содержит timestamp, job ID, этап, exit code, русское описание приложения и оригинальный вывод внешнего инструмента.
- URL может содержать приватные query-параметры/токены: не логировать полный URL без необходимости. По умолчанию редактировать чувствительную часть.
- Не логировать cookies, auth headers, секреты GitHub и другие credentials.

## 9. Предвидение проблем — обязательное правило

Перед реализацией каждого этапа агент обязан:
1. перечислить затрагиваемые подсистемы;
2. определить минимум 5 реалистичных failure cases, если этап нетривиальный;
3. проверить concurrency/cancellation/cleanup, если участвуют процессы или очередь;
4. проверить Windows-specific риски;
5. решить, какие тесты подтверждают исправность;
6. только затем реализовывать.

Нельзя считать задачу завершённой только потому, что happy path работает.

## 10. Изменения архитектуры

- Не менять стек, структуру очереди, формат persistence, схему зависимостей, release flow и naming policy молча.
- Если обнаружено, что исходное решение создаёт технический долг или ломает требование, сначала описать проблему и предлагаемое изменение.
- Избегать premature abstraction, но интерфейсы между download-engine, persistence и UI должны быть явными.

## 11. Git

- Production repository и Releases публичные: `Valturere/Mangar-Downloader`. Старый `Valturere/YTDLP-GUI-Mangar` остаётся private архивом. Секреты/runtime data не публиковать.
- Коммиты небольшие и логически цельные.
- Commit messages — на русском.
- Не смешивать рефакторинг и новую функцию без необходимости.
- Не коммитить generated build output, временные файлы, логи, загруженные видео, локальные tools binaries и секреты.
- Перед commit: format + lint + tests + production build для затронутой области.
- Перед release: выполнить skill `release-windows`.

## 12. Что нельзя делать без запроса пользователя

- Добавлять cookies browser extraction, прокси, субтитры, playlists UI, metadata editor, SponsorBlock, архив скачиваний, аккаунты, облачную синхронизацию, telemetry, analytics.
- Выполнять тихую автоматическую установку приложения: production updater проверяет PUBLIC Releases по TTL, установка только по явному click.
- Добавлять portable-сборку до стабильного installer workflow.
- Отправлять данные на внешний сервер.
- Удалять пользовательские файлы без явного действия пользователя.

## 13. Definition of Done

Изменение считается готовым, если:
- реализован требуемый сценарий;
- обработаны основные негативные сценарии;
- нет известных утечек процессов/temp для затронутого пути;
- тесты проходят;
- production build проходит;
- UI не ломается на целевых DPI/размерах, если изменение визуальное;
- документация обновлена, если изменилась архитектура или поведение;
- `git diff` просмотрен перед коммитом.

## 14. Verification policy — основной источник истины

**Изменённое проверяется глубоко. Смежное — разумной регрессией. Несвязанное — не гоняется без причины.**

Перед каждым этапом определить изменяемые файлы/подсистемы, риски, targeted tests, оправданные соседние регрессии и необходимость real/native/network smoke. Не копировать checklist предыдущего этапа механически.

- **Baseline:** после нетривиальных изменений — применимые format, Go vet и обычные unit tests (`go test ./...`), frontend format/typecheck/lint/production build. Production Wails build нужен для изменений самого приложения; для чистых docs/test/tooling изменений без влияния на приложение не нужен. Для чистых docs достаточно проверки документации/diff.
- **Targeted:** глубоко проверять изменённое. Scheduler: FIFO/max 3/Cancel/Retry/Remove/concurrency/race/integration. Tools: Detect/install/update/rollback/manifests/leases/integrity/isolation. Batch: parsing/indices/collisions/scheduler/large batch. Titlebar: native maximize/restore/minimize/state/accessibility/DPI. UI/CSS: соответствующие UI/visual/browser checks и build.
- **Cross-regressions:** только при пересечении boundary; для каждой назвать возможный сбой. Batch требует scheduler/publication integration. Titlebar сам по себе не требует download/FFmpeg/ToolManager/scheduler stress.
- **Real/native/network:** для изменённого поведения. Public network — extractor/download/network/tools integration, когда deterministic fixture недостаточна; интернет не использовать ради формального отчёта. Native — window/tray/dialog/shell или milestone. Real isolated tools install — dependency changes или milestone/release.
- **Full:** перед первым installer, GitHub Release, milestone/release candidate, крупной архитектурной переделкой или по явному запросу. Не default после каждого commit. Installer/clean-machine gates нужны, когда соответствующий milestone входит в задачу.
- **Race:** concurrency-sensitive изменённые Go packages, scheduler/process/tools/callbacks; полный набор перед milestone/release. CSS/UI без изменения Go concurrency не требует полного `-race ./...`.

Automated tests/smoke по умолчанию **не изменяют `%LOCALAPPDATA%\YTDLPGUIMangar`**. Использовать `t.TempDir()`, `.local`, dedicated smoke root/profile. Production profile допустим только при явно требующей его проверке, которую обозначить; проверка non-destructive, рабочие tools/data не удалять/заменять без явной необходимости. Зафиксировать current identities/manifests/runtime hashes до/после relevant suite. Старый destructive smoke не является разрешением трогать production.

Примеры: размер CSS-кнопки → frontend checks/relevant UI, без media/process stress; scheduler → Go/scheduler stress/race/process isolation, public download необязателен; tools install/update → tools tests/isolated real install, без большой queue UI; Release → full regression.

Отчёт разделяет Baseline checks, Targeted checks, Cross-regressions, Manual / real smokes и Skipped as not relevant. Для пропущенных важных тяжёлых checks кратко указать причину; нерелевантный smoke не считается незакрытым gate. Команды — `scripts/verify.ps1` (baseline), явные targeted switches и `-Full`; подробности в README. Навык `.codex/skills/verify-change/SKILL.md` следует этой политике.
